# QR-Menu SEO and Next.js Implementation Plans

Generated by the `improve` skill on 2026-08-07. These plans were written against commit
`f91421b`. They are intentionally reusable: the strategy section can be copied to another
product, while the numbered plans contain QR-Menu-specific paths and verification gates.

## Outcome

QR-Menu already has a credible technical SEO base: global metadata, robots rules, a sitemap,
canonical URLs and structured data for public menus. Its acquisition surface is the real gap.
Today, the sitemap exposes only the homepage, changelog and eligible customer menus
(`app/sitemap.ts:9-54`), while the landing page's "Resources" destination is an FAQ section
(`app/page.tsx:109-114`, `app/page.tsx:974-1025`). There is no blog or set of search-intent
landing pages.

The useful Family Photo AI pattern is a complete loop:

1. Record keyword clusters and the search intent/competitor pattern behind them.
2. Build one strong hub for each cluster and narrower pages only where intent is distinct.
3. Publish supporting articles from Markdown with page-specific metadata and Article schema.
4. Connect every page through contextual internal links, related content and product CTAs.
5. Put every canonical, indexable URL in the sitemap and measure it by page and query in
   Search Console.

Family Photo AI demonstrates that loop in `content/seo/_clusters.json`,
`src/app/[slug]/page.tsx:83-142`, `src/lib/blog.ts:25-114`,
`src/app/blog/[slug]/page.tsx:21-97`, and `src/app/sitemap.ts:13-89`.

Do not copy two weaknesses from the reference project:

- Do not create two articles for the same primary intent. Its
  `ai-family-photo-generator-family-portrait-from-separate-photos.md` and
  `create-family-portrait-from-separate-photos.md` are close enough to require a
  cannibalization review.
- Do not generate dozens of pages from a template until each has a distinct user problem,
  original examples and enough substance to deserve indexing. Google recommends
  people-first content, not mass-produced search-engine-first pages.

## Reusable SEO playbook

Use this sequence for QR-Menu or another product. Replace the example clusters, but keep the
gates and measurement discipline.

### 1. Establish the baseline

- Export the last 16 months of Search Console query, page, country and device data. Preserve
  both daily and query/page views so seasonality and cannibalization can be seen.
- Record indexed-page count, sitemap status, non-indexed reasons, Core Web Vitals, branded vs
  non-branded clicks, top landing pages, conversion rate and current referring domains.
- Define one primary conversion for organic traffic and instrument it before publishing.
- Compare the successful project's page-level changes against impressions and clicks by date.
  Correlation alone is not enough to attribute the gain to "having a blog."

### 2. Research search intent, not just keywords

- Start from product jobs, customer language, support questions and Search Console queries.
- For every candidate query, inspect the current results: page type, angle, freshness, SERP
  features, dominant competitors, and whether users want a tool, comparison, template,
  explanation or local provider.
- Cluster only queries that can be answered by the same best page. Assign exactly one primary
  page to each intent to avoid cannibalization.
- Score opportunities on product fit, intent proximity, evidence of demand, ability to add
  first-hand value, competition and effort. Never invent search volume.

### 3. Build a page map

- Homepage: broad category and brand promise.
- Commercial hubs: high-intent product/category problems.
- Narrow solution pages: distinct audiences or jobs, not synonyms.
- Blog guides: informational questions that naturally lead to the product.
- Comparison/template pages: only where the product can provide an honest, useful answer.
- Every page gets a primary intent, unique title/H1, clear answer, original examples, one main
  CTA, canonical URL, internal-link parents/children and an update owner.

### 4. Publish people-first content

- Lead with the answer. Add screenshots, examples, original workflows, measurements or lessons
  learned from the actual product.
- Demonstrate authorship and update dates. Cite reliable sources where factual claims need them.
- Use a descriptive title and H1, logical H2/H3 structure, useful image alt text, and concise
  snippets. Do not optimize to a word count or repeat a keyword mechanically.
- Link to the relevant product surface and two to four genuinely related pages.
- Merge or redirect overlapping content rather than letting similar pages compete.

### 5. Make discovery and interpretation reliable

- Render useful content in server HTML. Give every indexable page unique metadata and a
  self-referencing canonical.
- Include only canonical, indexable 200-status URLs in the sitemap, with truthful `lastModified`
  values. Keep private/auth/app pages noindexed and blocked where appropriate.
- Add only structured data that matches visible content. Validate it with Google's Rich Results
  Test and URL Inspection; markup does not guarantee a rich result.
- Provide visible breadcrumbs and keep them aligned with Breadcrumb structured data.
- Preserve fast LCP/INP/CLS, mobile usability and accessible navigation.

### 6. Operate a 90-day feedback loop

- Days 0-14: baseline, research, technical fixes and first briefs.
- Days 15-45: publish one hub and three to five high-quality supporting pages.
- Days 46-90: inspect queries and pages weekly; improve titles for high-impression/low-CTR pages,
  expand pages ranking near page one, consolidate overlap and strengthen internal links.
- Evaluate at 28, 56 and 90 days. Track impressions, clicks, CTR, average position, indexed URLs,
  organic conversions and assisted conversions by landing page. Avoid reacting to daily noise.

## Global verification gates

Every implementation plan must finish with:

```bash
npm run lint
npm run format:check
npx tsc --noEmit
npm run build
```

Expected result: all commands exit 0. Where a plan adds tests, `npm test` must also exit 0.

## Findings considered and rejected

- **A blog alone caused the reference project's growth**: not established without its Search
  Console exports and a dated page/change analysis. Treat blog, landing pages and technical SEO
  as a system and measure each landing page.
- **Meta keywords are a growth lever**: not worth prioritizing. The current list in
  `app/layout.tsx:18-26` does not replace intent-matched pages and useful content.
- **Enable experimental Cache Components immediately**: deferred. First take production
  baselines and update to the supported patch; adopt caching features only where measured route
  behavior justifies the migration cost.
- **Index dashboard/auth/onboarding pages**: rejected. They are not acquisition content and the
  existing robots/noindex posture is correct.
- **Publish every seed keyword as a templated page**: rejected. Validate distinct intent and the
  ability to provide original value first.
